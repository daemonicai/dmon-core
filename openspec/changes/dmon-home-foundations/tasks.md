## 4. Supervision

- [x] 4.1 Define the child descriptor — transport, endpoint, health check, timeout, startup order, adoption policy — so a child is expressed as configuration rather than a bespoke type. Enumerate the full inventory (network gateway, Dcal, Dmail, mlx reasoner, mlx triage, speech sidecar) and the read-only monitors (Tailscale, calendar sync, mail, egress) as descriptors, marking which are started in this change. (Satisfies "The child model accommodates the full inventory".)
- [x] 4.2 Implement reattach-first startup: health-check the endpoint, adopt a live process, spawn only when nothing answers. Track whether each child was adopted or spawned. (Satisfies "Children are adopted before they are spawned" — adopt and spawn scenarios.)
- [x] 4.3 Implement bounded health checking: every check carries a timeout, a check exceeding it is recorded as failed without blocking other children, and each child's health is published for the UI. (Satisfies "Each child is health-checked with a bounded timeout".)
- [x] 4.4 Implement crash detection with exponential backoff between restart attempts, and surface repeated failure rather than retrying silently. (Satisfies "Crashes are detected and retried with exponential backoff".)
- [x] 4.5 Implement dependency-ordered startup and reverse-ordered graceful shutdown, requesting graceful termination before escalating. (Satisfies "Startup and shutdown follow declared dependency order".)
- [x] 4.6 Place each **spawned** child in its own process group and kill that group on host exit; leave **adopted** children running. (Satisfies "Spawned children are killed by process group on exit" and "An adopted child outlives the host".)
- [x] 4.7 Register `Dmon.Network` as the one child started in this change, resolving its executable the way `dmonium`'s `NetworkManager` does (default `~/.dotnet/tools/ndmon`, overridable). **HUMAN VERIFICATION — do not tick without Product Owner confirmation.** Recipe:
  - **A — Install/build.** Run `make dmon-home-app`. Do **not** change `-configuration Release` or `-derivedDataPath home/.build-xcode` in `home/project.yml`/the Makefile without updating this recipe in the same block (carried from 3.4 — this recipe's paths are hard-coded to those flags). If `ndmon` is not at `~/.dotnet/tools/ndmon`, either run `make network` to build and install it there, or set `DMON_NETWORK_PATH` to an existing `ndmon` binary. A shell-exported `DMON_NETWORK_PATH` is **not** inherited by an app launched via `open` or Finder (GUI-launched processes on macOS do not inherit the launching shell's environment) — to use the override you must launch the binary inside the bundle directly: `DMON_NETWORK_PATH=/path/to/ndmon home/.build-xcode/Build/Products/Release/DmonHomeApp.app/Contents/MacOS/DmonHomeApp`. Note this costs the TCC bundle grant from 3.3 (the prompt keys on the bundle, not the raw binary) — acceptable here since this task exercises no microphone path.
  - **B — Cold start spawns.** Confirm nothing is already running: `pgrep -fl ndmon` should print nothing. Launch the app (`open home/.build-xcode/Build/Products/Release/DmonHomeApp.app`, or the direct-binary form above if using the override). Within about 30 seconds — `HostRuntime`'s default health-check interval, so the first "healthy" reading is not immediate — confirm `curl -sv http://127.0.0.1:5500` gets a response, and that the "Network Gateway" row in the app window reaches health `healthy` / supervision `normal`. **Failure looks like:** no `curl` response, or the row stuck at `unknown` (or showing `unhealthy` once a probe has run and failed) past 30s — the executable did not resolve or the process failed to spawn.
  - **C — Quit terminates what it spawned.** From B's still-running state, note the pid (`pgrep -fl ndmon`), quit the app (Cmd-Q). Confirm `pgrep -fl ndmon` now prints nothing. **Failure looks like:** the pid is still alive after quitting — a spawned descendant survived the host, which 4.6's "No spawned descendant survives" exists to prevent.
  - **D — Adoption, and adopted outlives the host.** Start `ndmon` manually first, independent of the app (e.g. `~/.dotnet/tools/ndmon &` — if you took the `DMON_NETWORK_PATH` override branch in A, substitute your own binary's path here instead). Note its pid. Launch the app — if using the override, this must be the **direct-binary form from A**, not `open`; `open` does not carry a shell-exported `DMON_NETWORK_PATH` into the app's environment, so the app would resolve its own default path instead and this phase would silently test the wrong thing. Confirm `pgrep -fl ndmon` still shows **exactly that same pid** — not a second one. Quit the app (Cmd-Q), then confirm `pgrep -fl ndmon` still shows that same pid running. **Failure looks like:** a second `ndmon` pid appearing after launch (adoption is broken, a duplicate gateway was spawned underneath the running one — the single most important thing this phase catches), or the pid disappearing after quit (an adopted child must not be killed). Clean up afterward: `kill` the manually-started process.
  (Satisfies "A live child is adopted" and "An adopted child outlives the host" — verified end-to-end against the real `ndmon` binary, complementing 4.6's unit-level proof of the same scenarios.)
